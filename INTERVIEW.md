# Как объяснить решение на собеседовании

Это описание **данного решения**, а не рассказ о личном опыте кандидата. Ответы из README исходного репозитория о прошлых проектах нужно дополнить своими реальными примерами.

## С чего начать демонстрацию

1. Открыть два разных браузерных профиля: `admin` и обычный игрок.
2. Создать раунд от администратора, открыть его вторым игроком.
3. Показать запрет тапов до старта и автоматический переход к игре.
4. Нажать 11 раз: счёт 20. Объяснить, почему бонус заменяет обычное очко.
5. Открыть третьего игрока `Никита`: запросы успешны, счёт 0.
6. Дождаться окончания, показать победителя и запрет новых тапов.
7. Запустить интеграционные тесты и открыть `server/src/rounds.ts`.

## Почему транзакции, а не mutex в Node

Mutex защищает только один процесс. При трёх backend каждый будет иметь собственный mutex. PostgreSQL — общее место синхронизации, поэтому блокируется строка раунда. Уровня READ COMMITTED достаточно для записи: все изменения этого раунда проходят через одну блокировку, порядок блокировок одинаковый.

Личные очки и общий счёт изменяются в одной транзакции: нельзя закоммитить только один из двух счётчиков. Тест с намеренной ошибкой на UPDATE общего счёта проверяет откат личной статистики.

## Почему clock_timestamp(), а не now()

В PostgreSQL `now()` — время начала транзакции. Пока запрос ждёт блокировку, реальное время может перейти за границу раунда. Поэтому после `FOR UPDATE` берётся `clock_timestamp()`, один раз через MATERIALIZED CTE. Проверка сравнивает настоящие PostgreSQL timestamp, без потери микросекунд при преобразовании в JavaScript Date.

Точкой принятия тапа считается проверка после захвата блокировки. Транзакция может закоммититься чуть позже окончания, но сам тап был принят в активном интервале. Время прихода HTTP-запроса на конкретный Node-сервер не используется.

## Почему общий счёт хранится, а не вычисляется SUM

ТЗ просит обновлять общий счёт при тапе. Храним агрегат и поддерживаем его в одной транзакции с личной статистикой. Это ускоряет чтение, но создаёт горячую строку. Для десяти участников это разумный компромисс. При большой нагрузке сначала измеряем очередь блокировок, latency и throughput, затем решаем, нужен ли агрегат при каждом тапе или можно считать/публиковать его асинхронно. Асинхронный агрегат меняет гарантию свежести данных.

## Почему REPEATABLE READ для деталей

При нескольких независимых SELECT в READ COMMITTED можно прочитать общий счёт до чужого commit, а личные очки — уже после. REPEATABLE READ даёт всем SELECT один снимок: total, mine и winner согласованы. Транзакция короткая и только читает.

## Почему opaque session, а не JWT

Нужна мгновенная проверка пользователя и отзыв сессии при logout. Общая PostgreSQL уже есть, нагрузка небольшая: случайный токен проще JWT, не требует синхронизации ключей или denylist. Цена — один JOIN к базе на авторизованный запрос. В cookie находится токен, в базе только его хеш. В нескольких backend не требуется общая память.

Это осознанный выбор для этого приложения. JWT может быть уместен при других требованиях; его подпись сама по себе не решает отзыв сессии и актуальность прав.

## Почему Fastify и простые сервисы

Маршруты занимаются HTTP и проверкой данных, AuthService — пользователями и сессиями, RoundService — игровой транзакцией. Зависимости передаются конструкторами. `buildApp` принимает подключение к БД, поэтому тест создаёт два экземпляра с отдельными пулами.

Для такого размера интерфейс репозитория поверх каждого Drizzle-запроса добавил бы мало пользы: самые важные гарантии уже привязаны к PostgreSQL. Нет необходимости имитировать переносимость на произвольную базу.

## Что происходит с ответами не по порядку

Каждый тап — отдельный POST. Если ответ на более ранний тап придёт позже, UI не откатывает уже подтверждённые очки: сравнивает счётчики тапов и общий максимум. То же правило применяется к polling. При сбое сети нет автоматического retry: без idempotency key нельзя знать, успела ли транзакция закоммититься. Следующий polling показывает фактический счёт.

Для гарантированного повторения запросов можно добавить клиентский UUID тапа и таблицу обработанных идентификаторов с уникальным ключом в той же транзакции. Это отдельная гарантия, которой ТЗ не требует.

## Что ещё стоит обсудить

- Победитель при ничьей: ТЗ не определяет правило. Здесь оно детерминированное, по имени и UUID.
- Роль по имени `admin` — требование тестового. Для настоящего публичного сервиса нужен отдельный процесс назначения прав.
- Защита от ботов, rate limiting и ограничение попыток входа — отдельные продуктовые и эксплуатационные требования. Ограничение по IP в памяти одного Node не решает проблему нескольких backend.
- Часы всех экземпляров Node не влияют на принятие тапа: используется время общей базы. Клиентский таймер приблизителен, сервер остаётся источником истины.
- Бонусы локальны для игрока и раунда. Перенос счётчика между раундами противоречил бы выбранной модели.
- Числа в БД — bigint, API использует JavaScript number. Для реалистичной нагрузки и максимальной длительности сутки точности достаточно; при выходе за MAX_SAFE_INTEGER контракт нужно переводить на десятичные строки.
- UUID удобны для ссылок и генерации идентификаторов. Для больших таблиц случайный UUID может ухудшать локальность B-tree; это нельзя объявлять бесплатным универсальным стандартом.
